## Decisions that touch your contracts - please confirm
1. **Line numbers are 1-based** in findings. If the extension sends 0-based `cursor.line`, A should add 1 before it reaches the pet's "trace line N" message.
2. **`line` is always an int; `0` means unknown** (test failure with no stack frame). Don't draw a line marker for 0.
3. **Contract 2 extension:** each result has an extra boolean `hidden`. For hidden tests `expected`/`actual` are always `null` and `message`
   is generic - the tutor and UI must not try to reveal them. Failures also carry the neutral `error_type` set listed in `lessons/README.md`;
   the student's line is in `message` as `... at solution.py:14`.
4. **Contract 1 extension (optional):** a `test_run` event may carry a `test_result` field (Contract 2 payload); `analyze` turns it into findings.
   Normally A calls `run_tests` itself and passes the result to `test_results_to_findings`.
5. `lesson` args accept a parsed dict, a path, or a lesson id (resolved under `LESSONS_DIR`, default `/lessons`).
6. **Signals vocabulary** (`rule:/test:/error:/diag:/rubric:`) in `lesson.yaml` is what maps evidence to `mistake_id` - C's `ingest_lesson`
   can ignore it or store it as `(:Mistake)-[:SIGNALLED_BY]->(:Signal)`. `prerequisites` are lesson ids; concept edges live in `lessons/concepts.yaml`.
7. `run_tests` raises `analysis.runners.RunnerError` for infrastructure problems (missing toolchain/solution/lesson). Do not turn those into mistakes.
8. Run `run_tests` in a worker thread/process: it blocks (typically 1-4 s, ~8 s if the code hangs).

## Kinds of findings (Contract 3)
`pattern` (static rule or rubric gap), `test_failure`, `diagnostic` (from editor diagnostics), `guess_spam` (`mistake_id: guess_and_check`, concept `debugging_by_tracing`).
